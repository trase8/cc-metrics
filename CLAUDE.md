# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Назначение

`cc-metrics` — приёмник телеметрии Claude Code для организации на плане Claude for Teams (~40 разработчиков).

**Единственная целевая метрика — факты использования скиллов**: когда и какой скилл запустили. Всё
остальное, что прилетает по OTel, — побочный поток, который отбрасывается.

Метрики **анонимные**: личность пользователя не хранится и не попадает даже в лог, хотя по проводу
приходит (см. «Данные» ниже). Это не настройка, а свойство приёмника — вопросы вида «кто чаще всех
запускает скилл» здесь принципиально без ответа.

## Приёмник

FastAPI-приложение, принимает OTLP/JSON на `POST /v1/logs`, пишет вызовы скиллов в Postgres
(если задан `DATABASE_URL`) и отдаёт их же на `GET /ui`. Разбито по слоям:

| Файл | Отвечает за |
| --- | --- |
| `config.py` | переменные окружения, логирование, авторизация (`require_token`, `require_ui_auth`), пул `asyncpg`, DDL/lifespan |
| `api.py` | `/v1/logs`, `/v1/metrics`, `/v1/traces` — разбор OTLP и запись в базу |
| `ui.py` | `/ui` — график по дням и HTML-страница |
| `main.py` | собирает `FastAPI()` из роутеров, `/health`, точка входа |

`api.py` и `ui.py` читают изменяемое состояние (`pool`) через `import config; config.pool`, а не
`from config import pool` — иначе увидели бы значение на момент импорта (`None`), а не то, что
`lifespan()` проставляет при старте.

Что важно знать про формат OTLP и уже учтено в коде:

- Приходит стандартная кодировка: `resourceLogs[].scopeLogs[].logRecords[]`, атрибуты — массив
  `{"key": ..., "value": {"stringValue": ...}}`. В OTLP/JSON `intValue` всегда строка.
- Экспортёр ждёт ответ вида `{"partialSuccess": {}}`.
- Ошибка обработки одной записи не должна ронять батч: иначе экспортёр начнёт слать его повторно.
- Тело может быть сжато gzip. Стоят потолки на размер тела и на объём распаковки — против gzip-бомбы.
- `/v1/metrics` и `/v1/traces` отвечают 200 и игнорируются: на клиентах эти сигналы выключены (у обоих
  экспортёров значение по умолчанию — `none`), но 404 здесь только путал бы при отладке.
- Разбирается **только JSON**. При `http/protobuf` приёмник отвечает 400 и пишет в лог, что менять.
- Если запись в базу упала — ответ `/v1/logs` **503**, а не 200: OTLP-экспортёр повторит батч, а
  уникальный индекс `(session_id, event_sequence)` не даст задвоить строки. Молча ответить 200 значило
  бы потерять события при любом сбое базы.

По умолчанию в лог идут только строки `SKILL`. Отфильтровать поток на стороне клиента нельзя — Claude Code
шлёт все события подряд, отбор возможен только здесь. Поэтому глушатся два источника шума: прочие события
и access-лог uvicorn, который иначе печатал бы строку на каждый батч. Ошибки, отказы по токену и стартовый
баннер остаются всегда.

| Переменная | Смысл |
| --- | --- |
| `DATABASE_URL` | подключение к Postgres. Пусто — пишем только в лог, без хранилища |
| `CC_METRICS_TOKEN` | Bearer-токен для `/v1/logs`, `/v1/metrics`, `/v1/traces`; пусто — проверка выключена |
| `CC_METRICS_UI_USER`, `CC_METRICS_UI_PASSWORD` | HTTP Basic для `/ui`; нужны обе, иначе страница открыта |
| `CC_METRICS_LOG_LEVEL` | `INFO` (по умолчанию) / `DEBUG` / `WARNING` / `ERROR` — уровень только нашего логгера |
| `CC_METRICS_LOG_ALL_EVENTS` | по умолчанию `0` — только `skill_activated`; `1` — весь поток событий |
| `CC_METRICS_ACCESS_LOG` | по умолчанию `0` — access-лог uvicorn заглушен; `1` — для отладки |
| `PORT` | порт (по умолчанию 4318 — стандартный для OTLP поверх HTTP) |
| `TZ` | пояс для времени в текстовом логе (`asctime` в `config.py`, идёт через `localtime`); без неё UTC |

`TZ` **не** влияет на разбивку по дням в `/ui`: `date_trunc('day', received_at)` там считается в таймзоне
сессии Postgres (по умолчанию UTC на большинстве установок, включая шаблон Coolify), а не в таймзоне
контейнера приёмника. Если понадобится сдвинуть границы суток графика на локальный пояс, менять нужно
`TimeZone` на стороне Postgres или добавлять `SET TIME ZONE` при подключении — переменная `TZ` для этого
не подходит.

```bash
uv run main.py           # http://127.0.0.1:4318, страница просмотра — /ui
uv run pytest            # tests/ — юниты api.py/ui.py + один сквозной тест GET /health
uv add <package>         # зависимости; правит pyproject.toml + uv.lock
uv add --dev <package>   # то же самое, но для dev-группы (pytest, httpx)
uv sync                  # привести .venv в соответствие с pyproject.toml
```

Окружение управляется **uv** (CPython 3.14). Не использовать `pip install` и не активировать venv вручную.
Линтера и форматтера в проекте нет — если понадобятся, добавлять через `uv add --dev`.

`pyproject.toml` содержит `[tool.pytest.ini_options] pythonpath = ["."]` — без этого `tests/` не видит
корневые модули (`main`, `config`, `api`, `ui`), потому что это не пакет с `__init__.py`, а плоский набор
файлов.

## Хранилище: таблица `skill_usage`

Единственная таблица, создаётся приёмником при старте (`CREATE TABLE IF NOT EXISTS`), отдельных миграций
нет. `DATABASE_URL` — стандартный DSN (`postgresql://user:pass@host:port/db`); схемы SQLAlchemy вида
`postgresql+asyncpg://` тоже принимаются, префикс срезается перед передачей в asyncpg.

Уникальный индекс `(session_id, event_sequence)` — не техническая деталь, а условие корректности: без
него повторная доставка батча задваивает счётчики использования скиллов, и незаметно.

Время в таблице одно — `received_at`, момент вставки строки. Его проставляет `DEFAULT now()` на стороне
Postgres, в `INSERT_SQL` колонки нет вовсе. Время события на машине разработчика (`timeUnixNano`,
`event.timestamp`) приходит по проводу, но не разбирается и не хранится: экспортёр батчит события
(по умолчанию раз в 5 секунд, `OTEL_LOGS_EXPORT_INTERVAL`) и повторяет доставку при сбоях, поэтому
`received_at` отстаёт от реального запуска скилла на секунды-минуты, а после работы офлайн — на часы.
Для метрики «сколько раз за день дёрнули скилл» это приемлемо, но
если однажды понадобится точное время запуска, вернуть его — значит завести колонку заново, и
исторические данные её уже не получат.

Побочный эффект идемпотентности: `ON CONFLICT ... DO NOTHING` не обновляет строку, поэтому при
повторной доставке батча в `received_at` остаётся время **первой** успешной вставки.

`/ui` — линейный график на Chart.js: ось X — день, ось Y — число вызовов, одна линия — один скилл.
Фильтры (скилл, диапазон дат — без пользователя, триггера и лимита, их убрали из формы) через
GET-параметры. Без `since`/`until` окно по умолчанию — последние 30 дней; шире 400 дней диапазон
обрезается с явной пометкой на странице, а не молча.

Цвет линии закреплён за скиллом по общему числу вызовов **за всё время** (`GLOBAL_RANKING_SQL` в
`ui.py`), а не по рейтингу внутри текущего фильтра — иначе при смене фильтра выжившие линии
перекрашивались бы (antipattern «recolor-on-filter» из скилла dataviz). Топ-7 получают цвет из
палитры, остальное сворачивается в линию «Другое» нейтрального серого — восьмой слот палитры
осознанно не занят. Состав «Другого» на странице не раскрывается — табличный вид под графиком убрали.
Узнать числа по редкому скиллу можно, назвав его в фильтре: линия останется одна, но метка у неё
всё равно будет «Другое», потому что рейтинг глобальный и фильтр его не пересчитывает. Это цена
отказа от «recolor-on-filter»: считать метки по фильтру значило бы вернуть перекраску.

Chart.js подключается с CDN зафиксированной версией и SRI-хешем (`sha384-...` в `ui.py`) — значит
обновлять версию нужно руками: скачать новый `chart.umd.min.js`, пересчитать хеш, поправить оба места.

Работает и при пустой базе, и без `DATABASE_URL` (явно говорит, что хранилища нет, вместо пустой
страницы или 500-й).

## Данные: событие `claude_code.skill_activated`

Логируется и когда скилл вызывает модель через тул `Skill`, и когда человек набирает `/команду`.

| Атрибут | Значение |
| --- | --- |
| `event.timestamp` / `timeUnixNano` | время события на машине разработчика — приходит, но не разбирается |
| `event.sequence` | монотонный счётчик внутри сессии |
| `skill.name` | имя скилла |
| `invocation_trigger` | `user-slash` (набрал руками) / `claude-proactive` (модель решила сама) / `nested-skill` |
| `skill.source` | `bundled` / `userSettings` / `projectSettings` / `plugin` |
| `skill.kind` | `workflow` у workflow-скиллов, иначе отсутствует |
| `plugin.name`, `marketplace.name` | владелец скилла, если он из плагина |

Личность приходит в стандартных атрибутах любого события (`user.email` при OAuth-логине — наш случай,
`user.account_uuid`, `user.id`), но приёмник её **выбрасывает**: `drop_identity()` в `api.py` отсекает
всё с префиксом `user.` сразу после сборки атрибутов — до записи в лог и до сборки строки для базы.
Один барьер на входе, ниже по коду личности в `attrs` уже нет. Отбираем по префиксу, а не по списку
ключей: Claude Code может добавить новый `user.*`-атрибут, и он не должен просочиться.

Из прочих стандартных атрибутов в таблицу попадают только `session.id` и `terminal.type`.
`organization.id`, `department`, `team.id` приходят, но не сохраняются — как и весь остальной поток
атрибутов: колонки `raw` со свободной формой больше нет, в базе лежат ровно те поля, что перечислены
в `INSERT_SQL`. Добавлять новое поле — значит добавлять колонку в `DDL`, элемент в строку
`handle_record()` и плейсхолдер в `INSERT_SQL`; эти три места связаны тестами в `tests/`.

`session.id` сохраняется намеренно — на нём держится уникальный индекс
`(session_id, event_sequence)`, то есть вся защита от задвоения при повторной доставке батча. С
личностью он не связан, но позволяет сгруппировать вызовы внутри одной сессии — если понадобится
убрать и это, придётся сначала придумать другой ключ идемпотентности.

При анализе не считай `user-slash` единственным «настоящим» использованием: `claude-proactive` — это
полноценный вызов, и для оценки полезности скилла он даже интереснее.

## Ловушка: без `OTEL_LOG_TOOL_DETAILS=1` данные бесполезны

У пользовательских скиллов и скиллов из сторонних плагинов `skill.name` подменяется на плейсхолдер
`custom_skill`. Целевые скиллы (`01-dev-pipeline:cr`, `01-dev-pipeline:arch-check`) попадают именно в эту
категорию — без флага придёт поток неразличимых `custom_skill`. Приёмник помечает такие строки в логе.

Плата за флаг: он включает логирование параметров тулов вообще — команды Bash и входные аргументы тулов
в событиях `tool_result` / `tool_decision`. По проводу это уйдёт в любом случае, отбрасывать нужно здесь.

## Конфигурация клиентов

Ставится централизованно в **Admin Settings → Claude Code → Managed settings**
([claude.ai/admin-settings/claude-code](https://claude.ai/admin-settings/claude-code)) — на машинах
разработчиков делать ничего не нужно. Для обкатки на одном человеке тот же блок кладётся
в личный `~/.claude/settings.json`.

Шесть переменных — это полный набор, каждая обязательна. Лишние в блоке не держим: они создают
впечатление, что что-то настроено, хотя не делают ничего.

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "http/json",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "https://cc-metrics.quickname.tech",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer <токен>",
    "OTEL_LOG_TOOL_DETAILS": "1"
  }
}
```

- События — сигнал **logs**, поэтому `OTEL_LOGS_EXPORTER=otlp` обязателен. Без него не уедет ничего,
  каким бы правильным ни был endpoint.
- `CLAUDE_CODE_ENABLE_TELEMETRY` при значении `"0"` выключает всё, остальные переменные обессмысливаются.
- `OTEL_EXPORTER_OTLP_PROTOCOL` **не имеет значения по умолчанию** — не задать её значит не отправлять
  ничего. Нам нужен именно `http/json`: приёмник разбирает только JSON.
- В `OTEL_EXPORTER_OTLP_ENDPOINT` указывается база **без** `/v1/logs` — путь экспортёр добавляет сам.
  В per-signal варианте `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` путь пишется целиком.

Чего в блоке осознанно нет:

- `OTEL_METRICS_EXPORTER` и `OTEL_TRACES_EXPORTER`: значение по умолчанию у обоих уже `none`. Единственный
  сценарий, где явный `none` что-то даёт, — у разработчика в шелле экспортнута своя
  `OTEL_METRICS_EXPORTER=otlp`, и тогда метрики поедут на наш endpoint. Если такое всплывёт, две строки
  вернуть дешевле, чем отлаживать.
- `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` и любые `..._TRACES_ENDPOINT`: включают span-трейсинг, который
  работает только в паре с `OTEL_TRACES_EXPORTER=otlp`. Нам трейсы не нужны, приёмник их не разбирает.
- `OTEL_RESOURCE_ATTRIBUTES` (раньше здесь стояло `department=rnd,team.id=ai-sdlc`): приёмник эти
  атрибуты не сохраняет. На уже настроенных клиентах можно оставить как есть — значения просто
  отбрасываются.
- `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_ASSISTANT_RESPONSES`, `OTEL_LOG_TOOL_CONTENT`,
  `OTEL_LOG_RAW_API_BODIES`: выключены по умолчанию, и включать их незачем — они гонят по проводу
  тексты промптов, ответов и тел запросов к API. Не путать с `OTEL_LOG_TOOL_DETAILS`, который нужен.
- OTel-конфигурация не применяется на лету — нужен полный перезапуск Claude Code.
- Редактировать managed settings может только **Owner / Primary Owner**; роль Admin страницу не видит.
- Каждый разработчик один раз увидит security-диалог (его вызывает непустой endpoint). Отказ завершает
  Claude Code.

## Деплой

Coolify, сборка из `Dockerfile`. `uv.lock` обязан быть в репозитории — зависимости ставятся с `--frozen`.
Healthcheck — `GET /health`, HTTPS терминирует Traefik самого Coolify.

Порт по умолчанию 4318, но берётся из `PORT`. Подходит любой вариант: «Ports Exposes» = 4318 в Coolify
либо `PORT=3000` под порт платформы. Несовпадение даёт 502 от Traefik на всех путях — это первое, что
стоит проверять, если домен отвечает, а сервис нет.
